## 1. Назначение и стек

Приложение предоставляет общий каталог акций с текущими ценами, индикатором направления изменения цены и графиком исторических котировок. Пользователь может зарегистрироваться, войти и управлять каталогом через HTML. Есть REST API, административный интерфейс, команда импорта и периодическая задача обновления цен.

Стек, зафиксированный в requirements.txt: Python (версия не закреплена), Django 4.1.7, Django REST Framework 3.14.0, django-filter 22.1, PostgreSQL через psycopg2-binary 2.9.5, Celery 5.2.7 с Redis 4.5.1, tinkoff-investments 0.2.0b50, Plotly 5.13.1. Интерфейс — серверные Django Templates, локальные стили Bootstrap, crispy-forms 2.0 и crispy-bootstrap3 2022.1. Конфигурация содержит WSGI и ASGI точки входа; специального асинхронного пользовательского протокола в проекте нет.

## 3. Архитектура и взаимодействие

Это Django-монолит с двумя приложениями: dashboard и user. HTML-ветка следует схеме URL → view → форма/ORM/сервис → шаблон → HTTP-ответ. REST-ветка: URL → DRF router → ShareViewSet → ShareSerializer и ORM → ответ API. Обе ветки используют одну таблицу Share.

Страница детали синхронно вызывает `get_graph(share)`: запрос к Tinkoff Invest API выполняется прямо во время обработки HTTP-запроса. Исторические свечи преобразуются в Plotly HTML; в БД история не записывается.

Отдельный процесс Celery Beat планирует `update_last_price`, Redis служит брокером, worker последовательно обходит акции, запрашивает Tinkoff API и обновляет PostgreSQL. Для каждой акции создаётся отдельный клиент API. Импорт выполняется отдельно командой `python manage.py add_shares`. Все эти процессы используют конфигурацию Django.

Сессии и аутентификация опираются на django.contrib.auth и SessionMiddleware/AuthenticationMiddleware; включена CSRF middleware, HTML POST-формы содержат CSRF-токены. Логгер `main` пишет в консоль и относительный файл `app.logs`. REST API не вызывается HTML-шаблонами: они используют собственные Django views.

## 4. Зависимости и внешние сервисы

- PostgreSQL: база `investing`, localhost:5432, учетные данные заданы в `config/settings.py`. Compose публикует тот же порт.
- Redis: брокер `redis://127.0.0.1:6379/0`; Compose публикует 6379. Хранилище результатов Celery явно не настроено.
- Tinkoff Invest API: `Client(TINKOFF_TOKEN)`, методы `instruments.shares`, `market_data.get_last_prices`, `get_all_candles`. Токен в исходной конфигурации пустой; работоспособность доступа не установлена.
- DRF и django-filter обеспечивают сериализацию, CRUD, пагинацию, фильтрацию и поиск. crispy-forms оформляет поля HTML-форм; Plotly создаёт график.
- Шаблон `dashboard/templates/dashboard/base.html` подключает CDN Plotly latest, jQuery 3.3.1 slim, Popper 1.14.6, Font Awesome 4.7.0, Moment 2.23.0 и Tempus Dominus Bootstrap 4 5.1.2. Наличие подключения не доказывает использование каждого компонента; отдельного календарного сценария в шаблонах не обнаружено.
- В requirements.txt также закреплены инфраструктурные/транзитивные пакеты: amqp, asgiref, async-timeout, billiard, cachetools, click и его расширения, grpcio, kombu, protobuf, pydantic, python-dateutil, pytz, six, sqlparse, tenacity, typing_extensions, vine, wcwidth и другие. Black 23.1.0 и isort 5.12.0 относятся к инструментам разработки. Есть одновременно `tinkoff==0.1.1` и `tinkoff-investments`; необходимость первого пакета отдельно кодом не установлена.
- README предлагает Eventlet и cryptography для Windows, но в requirements.txt они отсутствуют. Образы `postgres` и `redis` в Compose не закреплены по версии. Актуальность версий и совместимость с современными сервисами в рамках этого этапа не проверялись.

## 5. Модель данных

### Share

Источник: `dashboard/models.py`, класс `Share`; история схемы: `dashboard/migrations/0001_add_share.py` — `dashboard/migrations/0007_add_updated_at.py`.

| Атрибут | Тип и ограничения | Смысл |
|---|---|---|
| id | Неявный BigAutoField, первичный ключ | Локальный идентификатор |
| figi | CharField(255), unique, обязательный | Идентификатор внешнего инструмента |
| isin | CharField(255), обязательный | ISIN; уникальность не задана |
| name | CharField(255), обязательный | Наименование компании |
| ticker | CharField(10), unique, обязательный | Тикер |
| currency | CharField(20), обязательный | Валюта; справочник допустимых значений не задан |
| uid | CharField(255), unique, обязательный | Внешний UID, хранится строкой, не UUIDField |
| last_price | FloatField, null/blank | Последняя сохранённая цена |
| is_trend_high | BooleanField, null/blank | Направление сравнения с предыдущей ценой |
| updated_at | DateTimeField, auto_now, null/blank | Время сохранения через модель; ограничение фонового обновления см. ниже |

Внешних ключей у Share нет. Нет владельца записи, связи с пользователем, отдельных сущностей котировок, портфелей, сделок, стратегий, списков наблюдения и уведомлений. Последние перечислены в задании №4, но в исходном проекте не реализованы.

### Пользователь и системные сущности

`user/models.py` присваивает `User = get_user_model()`, собственной модели не определяет. `AUTH_USER_MODEL` не переопределён: используется стандартный User Django с идентификатором, username, password (хеш), email, именем/фамилией, флагами активности/персонала/суперпользователя, датами входа/регистрации и связями многие-ко-многим с группами и разрешениями. Это описание стандартной модели, следующей из конфигурации, а не локальной миграции. Регистрация заполняет username и email одним адресом (`RegistrationForm.save`). Глобальная уникальность email на уровне модели специально не добавлена, проверка сделана в форме.

Сессии, группы, разрешения, content types и журнал администратора предоставляются стандартными Django-приложениями. При отсутствии переопределения backend сессий следует стандартное хранение сессий в БД. Реальная применённая схема БД не проверена.

## 6. Обработка запросов и БД

| Маршрут | Обработчик и данные |
|---|---|
| `/` | ShareListView: ORM-список, сортировка name, 100 записей на HTML-страницу |
| `/<int:pk>` | ShareDetailView.get: `Share.objects.get(id=pk)`, внешний API и график |
| `/create`, `/update/<int:pk>` | ShareCreateView/ShareUpdateView: ModelForm, валидация, сохранение, redirect на `/` |
| `/delete/<int:pk>` | ShareDeleteView: GET подтверждение, POST удаление, redirect на `/` |
| `/userlogin/`, `/userregistration/`, `/userlogout/` | AuthView, RegistrationView, LogoutView; пути получаются из префикса `user` без завершающего `/` |
| `/api/v1/shares/`, `/api/v1/shares/<pk>/` | ShareViewSet: стандартные list/create/retrieve/update/partial_update/destroy DRF |
| `/admin/` | Стандартный Django admin, регистрация ShareAdmin |

HTML-изменения защищены `IsUserAuthenticatedMixin.test_func`; анонимный посетитель перенаправляется на каталог. Владение акциями не проверяется, поскольку его нет в модели. ModelForm использует `fields = '__all__'`: редактируемые поля Share, включая uid, цену и тренд; автоматические id и updated_at не становятся вводимыми полями.

API использует `Share.objects.all()`, ModelSerializer и стандартные механизмы DRF. В проекте не заданы permission_classes или DEFAULT_PERMISSION_CLASSES; из стандартного AllowAny следует публичность операций API (расхождение с HTML — дефект/вопрос политики доступа). Стандартные SessionAuthentication/BasicAuthentication и особенности CSRF для session-запросов не равнозначны запрету анонимных операций.

Сериализатор выдаёт id, figi, isin, name, ticker, currency, last_price, is_trend_high, updated_at; uid отсутствует. id и auto_now updated_at по стандартному ModelSerializer доступны только для чтения. Проверки длины, обязательности и уникальности выводятся из модели и сериализатора; явных бизнес-проверок FIGI/ISIN/валюты, положительной цены или наличия инструмента у провайдера нет.

Импорт использует `get_or_create` со всеми шестью справочными полями. Задача обновления читает все Share и для каждой делает `filter(id=...).update(...)`; явных транзакций на весь импорт/обновление нет, ручного SQL нет. Исключения обновления логируются, цикл продолжает работу с другими акциями; пользователь не получает отдельного уведомления об ошибке. Временная метка котировки возвращается сервисом, но не сохраняется.

## 7. Восстановленные функциональные требования и сценарии

Ниже перечислены конкретные поддержанные кодом возможности. Ограничения и дефекты вынесены в раздел 8. Успех сценариев зависит от рабочего окружения и корректных входных данных.

1. **Просмотр общего каталога.** Посетитель открывает `/`, видит тикер-ссылку, название, ISIN, цену и валюту; при пустом списке — «Акций еще нет». Список сортируется по имени, разбивается по 100 записей; переход — через `?page=`. Подтверждение: `dashboard/views.py`, `ShareListView`; `dashboard/templates/dashboard/list.html`, шаблон списка.
2. **Визуализация направления цены.** В каталоге сохранённый истинный is_trend_high окрашивает ячейку цены зелёным, иное значение — розовым. Сценарий: посетитель сравнивает цветовые индикаторы строк. Подтверждение: `dashboard/templates/dashboard/list.html`, условие `share.is_trend_high`; источник данных — `dashboard/models.py`, `Share`.
3. **Просмотр карточки и графика.** Посетитель переходит по тикеру и видит имя, цену, валюту, updated_at и линейный красный график. Запрашиваются дневные свечи начиная с `now() - timedelta(days=180)` по FIGI. Подтверждение: `dashboard/views.py`, `ShareDetailView.get`; `dashboard/services/graph.py`, `get_graph`; `dashboard/templates/dashboard/detail.html`. Выбора периода пользователем нет.
4. **Регистрация с автоматическим входом.** Посетитель открывает форму регистрации, вводит email и два пароля; при корректных данных создаётся стандартный пользователь, выполняется login и переход на каталог. Форма требует email и оба пароля, проверяет формат email, совпадение паролей и наличие пользователя с таким email. Подтверждение: `user/forms.py`, `RegistrationForm.clean`, `RegistrationForm.save`; `user/views.py`, `RegistrationView.get/post`. Обработка некоторых невалидных данных дефектна, см. раздел 8.
5. **Вход по email и паролю.** Посетитель открывает форму, отправляет учетные данные; email приводится к нижнему регистру, используется как username в authenticate. При успехе создаётся сессия и открывается каталог; при отказе аутентификации отображается сообщение о неверном логине/пароле. Подтверждение: `user/views.py`, `AuthView.get/post`; `user/forms.py`, `AuthForm`; `user/templates/user/auth.html`.
6. **Выход из сессии.** Пользователь переходит по ссылке выхода, выполняется logout и переход на каталог. В шапке авторизованному пользователю показывается email и «Выход», остальным — «Войти». Подтверждение: `user/views.py`, `LogoutView.get`; `dashboard/templates/dashboard/base.html`.
7. **Добавление акции через HTML.** Вошедший пользователь открывает «Добавить», заполняет редактируемые поля Share, сохраняет; валидная запись попадает в общий каталог, после сохранения открывается список. Применяются обязательность, максимальные длины и уникальность figi/ticker/uid модели. Подтверждение: `dashboard/views.py`, `ShareCreateView`, `IsUserAuthenticatedMixin.test_func/handle_no_permission`; `dashboard/forms.py`, `ShareModelForm.Meta`; `dashboard/models.py`, `Share`.
8. **Редактирование акции через HTML.** Вошедший пользователь выбирает «Редактировать», меняет поля и сохраняет общую запись; после успеха возвращается в каталог. Подтверждение: `dashboard/views.py`, `ShareUpdateView`, `IsUserAuthenticatedMixin`; `dashboard/forms.py`, `ShareModelForm`; `dashboard/templates/dashboard/create.html`.
9. **Удаление акции через HTML с подтверждением.** Вошедший пользователь открывает «Удалить», видит название инструмента, подтверждает POST-формой; запись удаляется, открывается каталог. Подтверждение: `dashboard/views.py`, `ShareDeleteView`, `IsUserAuthenticatedMixin`; `dashboard/templates/dashboard/delete.html`.
10. **Чтение акций через API.** Клиент получает коллекцию GET `/api/v1/shares/` либо объект GET `/api/v1/shares/<pk>/` с полями ShareSerializer. Коллекция поддерживает limit/offset, размер по умолчанию 100. Подтверждение: `dashboard/api/v1/views.py`, `ShareViewSet`; `dashboard/api/v1/serializer.py`, `ShareSerializer.Meta`; `dashboard/api/v1/router.py`, `router.register`; `config/settings.py`, `REST_FRAMEWORK`. CRUD-действия наследуются от ModelViewSet.
11. **Отбор и порядок коллекции API.** Клиент передаёт точные фильтры `name`, `ticker`, сортировку `ordering=name`/`ticker` (в том числе с минусом для обратного порядка), либо `search` для регулярного выражения по имени. Подтверждение: `dashboard/api/v1/views.py`, `ShareFilter.Meta`, `ShareViewSet.filter_backends/ordering_fields/search_fields`; префикс `$name` задаёт regex-поиск DRF. Обычного HTML-поиска не реализовано.
12. **Изменение каталога через API.** ModelViewSet предоставляет POST коллекции, PUT/PATCH отдельного объекта и DELETE объекта; изменения проходят через ShareSerializer, удаление — ORM. Сценарий: API-клиент меняет name существующей акции или удаляет её. Подтверждение: `dashboard/api/v1/views.py`, `ShareViewSet`; `dashboard/api/v1/serializer.py`, `ShareSerializer`. Создание имеет проблему отсутствующего uid; публичный доступ и это ограничение не являются желаемыми требованиями, см. раздел 8.
13. **Операторский импорт справочника.** Оператор запускает `python manage.py add_shares`; команда получает инструменты у провайдера и вызывает get_or_create для figi, name, isin, ticker, currency, uid. Полностью совпадающие записи повторно не создаются; цены команда не загружает. Подтверждение: `dashboard/management/commands/add_shares.py`, `Command.handle`. Поведение при изменении справочных полей описано как дефект ниже.
14. **Периодическое обновление сохранённых цен.** При работающих Beat, worker и брокере задача назначается каждые 10 секунд, обходит акции, получает последнюю цену по FIGI и сохраняет цену/тренд. Для двух сравнимых цен снижение даёт False, увеличение или равенство — True. Ошибка одной акции логируется и не останавливает обход остальных. Подтверждение: `config/celery.py`, `app.conf.beat_schedule`; `dashboard/tasks.py`, `update_last_price`; `dashboard/services/market_data.py`, `get_last_data`. Это обновление БД; автоматической перезагрузки страницы нет.
15. **Административное управление акциями.** Пользователь с необходимым стандартным доступом Django admin открывает `/admin/`, просматривает акции, ищет по figi/isin/name/ticker и управляет полями, указанными в ShareAdmin. Подтверждение: `config/urls.py`, `urlpatterns`; `dashboard/admin.py`, `ShareAdmin.list_display/search_fields/fields`. Разрешения и CRUD наследуются от Django admin, не от HTML-mixin.

## 8. Дефекты, неоднозначности и противоречия

Это результаты статического анализа; ошибки не воспроизводились запуском. Они не являются функциональными требованиями.

1. **Блокирующая конфигурация.** `config/settings.py`: SECRET_KEY пустой, токен пустой. Первый препятствует штатной работе механизмов Django, требующих ключ, второй — авторизованным запросам провайдера. DEBUG=True, пустой ALLOWED_HOSTS и фиксированные пароли БД не являются готовой производственной конфигурацией.
2. **Несогласованный контроль доступа.** `ShareCreateView/ShareUpdateView/ShareDeleteView` требуют вход, а `ShareViewSet` не задаёт permissions; стандартный AllowAny позволяет обходить HTML-ограничение через API. Требуемая политика доступа неизвестна. Все акции общие; персональное владение отсутствует.
3. **Потеря дробной части цены.** `get_last_data` читает `resp.price.units`, `get_graph` — `candle.close.units`; nano не учитывается. FloatField также не обеспечивает точную десятичную арифметику. Показанные цены/графики могут быть неточными.
4. **Неверная семантика времени обновления.** `update_last_price` использует QuerySet.update без updated_at: auto_now не срабатывает. Время ответа провайдера (`detetime`) игнорируется. Карточка подписывает updated_at как время последнего обновления, хотя фоновая цена меняется без него. `0007_add_updated_at.Migration` не содержит blank=True в отличие от модели — небольшое расхождение состояния миграции и модели, фактическая новая миграция не проверялась.
5. **Неполный контракт создания API.** `ShareSerializer` не содержит обязательный уникальный uid. Переданный uid из теста не включён в сериализуемые поля. При стандартном создании строкового поля Django отсутствующее значение может стать пустой строкой: первая такая запись может сохраниться, следующая столкнётся с уникальностью. Это риск, выведенный из кода, а не воспроизведённый результат. Тест `DashboardTests.test_share_create` не доказывает корректность uid и повторного создания.
6. **Ошибки обработки невалидной регистрации.** `RegistrationForm.clean` обращается к cleaned_data через индексы даже после ошибок отдельных полей: возможен KeyError. `RegistrationView.post` предполагает наличие `form.errors['__all__']`, хотя ошибки могут относиться к полям. Шаблон показывает только общий error, а не ошибки всех полей.
7. **Пароли и email.** RegistrationForm не вызывает настроенные AUTH_PASSWORD_VALIDATORS. Регистрация не приводит email/username к нижнему регистру, а AuthView.post приводит: адрес со смешанным регистром может создать проблему последующего входа. Проверка email в форме не заменяет уникальное ограничение БД и не защищает от гонки одновременных регистраций.
8. **Валидация входа обходится.** AuthView.post не вызывает AuthForm.is_valid и читает form.data по ключам. Неполный POST может дать KeyError; поле EmailField фактически не проверяется сервером этой ветки.
9. **Ошибки карточки не преобразуются в понятный ответ.** ShareDetailView.get использует objects.get без get_object_or_404; отсутствующий id приводит к необработанному DoesNotExist. Ошибки получения свечей также не перехватываются; карточка зависит от сети и провайдера при каждом открытии.
10. **Импорт не обновляет справочник безопасно.** Command.handle использует все поля как условия get_or_create. При совпадении уникального FIGI и изменении name/другого поля возможна попытка вставки с IntegrityError вместо обновления. Исключения не обрабатываются. Миграция `0003_add_uuid` добавляет unique uid с временным default='', что может конфликтовать при нескольких уже существующих строках.
11. **Неопределённое начальное направление.** При last_price=None сравнение в update_last_price вызывает исключение, логируется и тренд становится True. Равенство также маркируется True, хотя verbose_name — «Растет цена». В HTML None отображается тем же цветом, что снижение. Нужны отдельные правила для неизвестного/неизменившегося значения.
12. **Расписание названо неверно.** Ключ `add-every-5-min` в config/celery.py противоречит `schedule=10.0` (10 секунд). Срок выполнения задачи допускается до 30 минут; блокировки перекрывающихся запусков и явной retry-политики нет. Ожидаемый период и поведение при задержках требуют уточнения.
13. **Нестандартные URL учетной записи.** `path('user', include(...))` формирует `/userlogin/` и аналогичные адреса вместо ожидаемого по обычной структуре `/user/login/`. Ссылки через reverse остаются согласованными с текущим кодом; является ли это ошибкой требований, неизвестно. Logout изменяет сессию через GET.
14. **Ограничения валидации и сортировки.** Нет проверки положительности цены, формата внешних идентификаторов и допустимой валюты. API имеет limit/offset без заданной сортировки по умолчанию; стабильность страниц при изменениях не обеспечена. Уникальность ticker глобальна — её пригодность для разных рынков не подтверждена требованиями.
15. **Окружение и воспроизводимость.** Compose монтирует репозиторий в `/app` контейнера БД, отдельного volume для каталога данных PostgreSQL не задаёт; сохранность БД при пересоздании не обеспечена явной конфигурацией проекта. Версии образов не закреплены, полного сценария первичной настройки/миграций/создания администратора в README нет. Доступность CDN и совместимость SDK не проверялись.
16. **Пределы существующих тестов.** DashboardTests не покрывает регистрацию, права HTML/API, фоновые цены, импорт, график, фильтры и повторное API-создание без uid. Тесты не запускались; наличие assert не является результатом проверки. Проверки отсутствующих объектов используют фиксированные id, что создаёт предположение о состоянии тестовой БД.

## 10. Проверка исходного анализа при выполнении задания №3

Разделы 1–9 выше сохраняют описание **исходной версии**. Фразы «не запускалось»
в них относятся к этапу заданий №1–2. Текущее поведение описано отдельно ниже.

Уточнения собственных выводов после проверки:

- Пункт 8.4: отсутствие `blank=True` в миграции 0007 **не означает рассогласование**.
  Django DateTimeField с `auto_now=True` сам задаёт `blank=True`, `editable=False`,
  а при deconstruct убирает эти неявные аргументы. Первоначальное предположение
  о возможной лишней миграции по blank было неточным. Реальный дефект —
  QuerySet.update не записывал время; теперь семантика времени изменена явно.
- Пункт 8.1: пустой SECRET_KEY не обязательно останавливает импорт настроек или
  каждый запрос. Он вызывает ImproperlyConfigured при обращении к ключу,
  например в механизмах подписи/сессий. В новой конфигурации проверка намеренно
  выполняется сразу при загрузке настроек.
- Пункт 8.15: отсутствие явного именованного volume PostgreSQL само по себе
  не доказывает потерю данных при любом пересоздании: образ объявляет свой volume.
  Риск связан с жизненным циклом анонимных volumes и повторным подключением.
  В новой Compose-конфигурации используется явно именованное хранилище.
- Предположение о коллизии uid в миграции 0003 проверяется тестом обновления
  двух старых записей. Исправленная миграция выдаёт разные `legacy-<pk>` вместо
  одного пустого default. Уже применённые миграции существующей БД не
  переисполняются; импорт по FIGI может восстановить настоящий uid.
- Не запускали исходную версию с исходными зависимостями: утверждения о её
  runtime остаются статическими выводами. Тесты выполняются для модернизированного
  приложения; они не выдаются за воспроизведение всех ошибок исходника.

## 11. Модернизация: отдельные решения и реализованные изменения

Задание №3 выполнялось только в текущей копии и ветке `agent-codex`, без других
агентов. Возможности задания №4 не реализованы.

1. Использован установленный Python 3.14.7, отдельный `.venv`. Django 5.2.18 LTS,
   DRF 3.18.3, django-filter 25.2, Celery 5.6.3, Redis client 6.4.0,
   psycopg 3.3.6, Plotly 6.9.0; все транзитивные версии закреплены в requirements.
   Django 5.2 поддерживает Python 3.14 начиная с 5.2.8:
   [официальная документация](https://docs.djangoproject.com/en/5.2/releases/5.2/).
2. Секреты/БД/источник/брокер/период читаются из окружения или локального `.env`.
   Добавлен `.env.example` без секретов. SQLite по умолчанию, PostgreSQL сохранён.
3. Каталог общий, чтение публичное. Изменения HTML/API требуют входа, session API
   требует CSRF. Admin сохраняет стандартные права. API включает обязательный uid,
   стабильный порядок по умолчанию, поиск по имени/тикеру, прежние фильтры и ordering.
4. Исправлены формы регистрации/входа, ошибки отдельных полей, парольные валидаторы,
   нормализация email и обработка конфликта регистрации. Выход переведён в POST;
   канонические URL `/user/login/`, `/user/registration/`, `/user/logout/`.
5. Неизвестная карточка возвращает 404. Ошибка провайдера графика показывает
   объяснение вместо падения страницы. Plotly встроен в ответ; CDN убраны из базы.
6. Реальная интеграция сохранена через официальный REST T-Invest вместо старого SDK:
   импорт, последние цены и дневные свечи. Таймаут 15 секунд, ошибки без токена
   явные, переключения на demo при сбое нет. Контракт сверялся с
   [официальной спецификацией](https://github.com/Tinkoff/investAPI/blob/main/src/docs/swagger-ui/openapi.yaml).
7. DemoProvider выдаёт только три вымышленных DEMO-инструмента с фиксированными
   ценами/временем и 180 точками. В HTML есть явная маркировка demo, сохранённые
   цены имеют источник `demo/tbank/manual/unknown`, в том числе в API.
8. Decimal учитывает nano. ExactPriceField хранит SQLite-цену как десятичный текст,
   PostgreSQL — NUMERIC(24,9). Тест проверяет все 24 значащих цифры. Из прежнего
   FloatField уже утраченную точность миграция не восстанавливает.
9. Время updated_at теперь — время котировки UTC. Тренд: первая цена/равенство null,
   рост true, снижение false; null отображается нейтрально. Ручная цена получает
   source=manual и очищает время/тренд. Изменение справочных полей время не меняет.
   Старые auto_now-времена/тренды сброшены миграцией 0008 как недостоверные.
10. Celery/Redis сохранены. Период по умолчанию 300 секунд, настраивается через
    PRICE_UPDATE_SECONDS. Просроченные/дублированные котировки пропускаются;
    отдельная ошибка не останавливает остальные акции. PostgreSQL использует
    блокировку строки. SQLite предназначен для локального одного worker;
    распределённая нагрузка и отказоустойчивость не подтверждены.
11. Импорт идемпотентно обновляет справочник по FIGI; конфликт уникальности
    откатывает весь импорт. Добавлена синхронная команда update_prices для проверки
    того же алгоритма без Redis. Накопления истории цен в БД не добавлено.
