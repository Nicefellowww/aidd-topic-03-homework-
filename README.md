# Investing Demo — задания №3 и №4

Общий каталог акций: HTML CRUD, регистрация, вход/выход, REST API, admin,
импорт инструментов, график дневных свечей за 180 дней и обновление цен Celery.
Добавлены персональные наблюдения, виртуальные портфели, накопленная история
и симулятор стратегий. Все сделки исключительно виртуальные.

Проверенное окружение: macOS arm64, Python **3.14.7**, Django **5.2.18 LTS**.
Все установленные зависимости закреплены в `requirements.txt`; системные сервисы
для локального демо не нужны. Django 5.2 поддерживает Python 3.14 начиная с 5.2.8:
[официальные release notes](https://docs.djangoproject.com/en/5.2/releases/5.2/).

## Первый запуск на macOS

Команды выполняются из корня текущей копии. Нужен уже установленный Python 3.14.

```sh
python3.14 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
cp .env.example .env
python -c 'from pathlib import Path; import secrets; p=Path(".env"); p.write_text(p.read_text().replace("DJANGO_SECRET_KEY=\n", "DJANGO_SECRET_KEY=" + secrets.token_urlsafe(48) + "\n"))'
python manage.py migrate
python manage.py add_shares
python manage.py update_prices
python manage.py runserver 127.0.0.1:8000
```

Если `.venv` и `.env` уже созданы, выполните `source .venv/bin/activate`,
`python manage.py migrate` и команду запуска сервера. Не перезаписывайте существующий `.env` при повторном запуске.
Локальный `.env` автоматически читается; переменные процесса имеют приоритет.
Секрет обязателен, в репозиторий `.env` и SQLite не попадают.

Откройте [каталог](http://127.0.0.1:8000/), карточку по тикеру,
[регистрацию](http://127.0.0.1:8000/user/registration/) и
[API](http://127.0.0.1:8000/api/v1/shares/).
После регистрации можно создавать, редактировать и удалять общие акции.
Выход — POST с CSRF через кнопку в шапке. Пароли проверяются валидаторами Django;
email регистрации нормализуется в нижний регистр и используется как username.
Для [admin](http://127.0.0.1:8000/admin/) создайте отдельного администратора:

```sh
python manage.py createsuperuser
```

Чтение HTML/API публично; запись требует аутентификации. API поддерживает сессию
с CSRF и BasicAuthentication для локального тестирования (вне localhost нужен HTTPS).
Admin сохраняет стандартные ограничения staff и permissions.
Примеры API:

```sh
curl 'http://127.0.0.1:8000/api/v1/shares/?ticker=DEMO1'
curl 'http://127.0.0.1:8000/api/v1/shares/?search=DEMO&ordering=-ticker&limit=2&offset=0'
```

Фильтры точного совпадения: `name`, `ticker`; поиск подстроки без учёта регистра:
`name`, `ticker`; сортировка: `name`, `ticker` с необязательным `-`.
Порядок по умолчанию `name, pk`. При создании обязательны
`figi`, `uid`, `isin`, `name`, `ticker`, `currency`; `figi`, `uid`, `ticker` уникальны.
Цена передаётся строкой десятичного числа. `updated_at`, `price_source`,
`is_trend_high` доступны в API только для чтения.

## Источники и правила цен

По умолчанию `MARKET_DATA_SOURCE=demo`: три вымышленных инструмента DEMO1–DEMO3,
180 воспроизводимых дневных точек, фиксированное время котировки
2026-01-15 12:00 UTC и цены 100/200/300 + 0.123456789. Это **демонстрационные
данные, не реальные котировки**. Предупреждение отображается на страницах;
`price_source` у каждой сохранённой цены показывает `demo`, `tbank`, `manual`
или `unknown` для унаследованных записей. Смена источника не меняет происхождение
уже сохранённых цен. Demo не выдаёт цены для произвольных реальных инструментов,
а T-Invest не запрашивает DEMO-инструменты. При смешанном каталоге задача
продолжает обработку, логируя ошибки отдельных акций.

Для реального провайдера задайте в `.env` `MARKET_DATA_SOURCE=tbank` и
`TINKOFF_TOKEN=<ваш токен>`, затем перезапустите сервер/worker/beat, выполните
`add_shares` и `update_prices`. Используется официальный HTTPS REST T-Invest:
[контракт API](https://github.com/Tinkoff/investAPI/blob/main/src/docs/swagger-ui/openapi.yaml),
[market data](https://developer.tbank.ru/invest/api/market-data-service).
Устаревший Python SDK заменён стандартным HTTP-клиентом с таймаутом 15 секунд;
автоматического переключения с реальных данных на demo нет.
Импорт сопоставляет по FIGI, обновляет справочные поля и сохраняет цены;
при конфликте уникальных идентификаторов весь импорт откатывается.
`legacy-<pk>` после старой миграции — временный UID; импорт реального справочника
обновляет его по FIGI. Уникальность тикера сохранена из исходной модели.

`units + nano / 10^9` рассчитывается через Decimal. Хранятся до 15 целых и 9 дробных
цифр: PostgreSQL NUMERIC(24,9), SQLite — десятичный текст, исключающий преобразование
через REAL. Это обеспечивает точность дробных частей в обоих локальных режимах.
Потерянную ранее дробную часть исходных FloatField/ответов без nano восстановить
без нового запроса провайдера невозможно. График использует полную цену свечи;
числа при отрисовке ограничены точностью JavaScript. Plotly встроен в HTML,
доступ к CDN для графика не требуется. Накопленная история БД доступна отдельно
по ссылке из карточки и не заполняется свечами провайдера.

`updated_at` означает **время котировки провайдера в UTC**, а не время HTTP-запроса
или изменения названия. Первая цена: тренд неизвестен (`null`); рост: `true`,
снижение: `false`, равенство: `null` (нейтральный цвет, как неизвестное состояние).
Ответ с временем меньше или равным сохранённому игнорируется; ошибки оставляют
последнюю цену и время без изменений. Ручное изменение цены через HTML/API/admin
маркируется `manual`, очищает время и тренд: время рыночной котировки неизвестно.
При миграции старые ненадёжные auto_now-времена и тренды очищаются.

## Фоновая работа и PostgreSQL

По умолчанию период `PRICE_UPDATE_SECONDS=300` (5 минут), только положительное
число секунд. `update_prices` запускает тот же код синхронно без брокера.
Для фонового режима нужны уже доступные Redis и два отдельных терминала с
активированным `.venv`:

```sh
celery -A config worker -l info --pool=solo --concurrency=1
celery -A config beat -l info
```

На macOS локально используйте один worker и один beat. Таймаут задачи 180 секунд;
новая попытка после ошибки — следующий период. Задачи в очереди имеют expires,
старые котировки не перезаписывают новые; PostgreSQL блокирует строку при записи.
SQLite предназначен для небольшого локального запуска, его блокировки не заменяют
многопроцессную эксплуатацию PostgreSQL. При долгом импорте/большом каталоге нужно
подобрать период/таймаут под ограничения провайдера. Системные сервисы автоматически
не устанавливаются.

Для PostgreSQL задайте `DB_ENGINE=postgresql` и все `POSTGRES_NAME`, `POSTGRES_USER`,
`POSTGRES_PASSWORD`, `POSTGRES_HOST`, `POSTGRES_PORT` из `.env.example`, затем
`python manage.py migrate`. SQLite и PostgreSQL — отдельные БД, автоматического
переноса данных между ними нет. При уже установленном Docker можно по желанию
поднять сервисы проекта (после задания пароля):

```sh
docker compose up -d db redis
```

Compose сохраняет PostgreSQL в именованном volume и публикует порты только на
127.0.0.1. Эта команда в текущем окружении не проверена: Docker отсутствует.

## Задание №4: правила и архитектура

- `/watches/`: один персональный список на пользователя, акция в нём уникальна.
  Добавление существующей акции изменяет направление (`≤` / `≥`) и цель.
  Цель положительна. Отслеживание начинается **со следующей новой котировки**:
  сохранённые до добавления/изменения записи не создают уведомлений. Первое
  выполнение условия создаёт уведомление, дальнейшие цены внутри условия — нет.
  Только выход из условия и новый вход разрешают повторное уведомление.
  Изменение цели заново вооружает правило; прочтение уведомления — нет.
  Удаление акции из списка удаляет её уведомления. Отметка «Прочитано» — POST.
- `/portfolios/`: несколько портфелей; у каждого одна валюта, сделки в другой
  валюте отвергаются. Конвертации и общего итога разных валют нет. Покупка
  увеличивает позицию; средняя = (старое количество × средняя + новая стоимость)
  / новое количество. Продажа сохраняет среднюю оставшейся позиции;
  реализованный П/У = количество продажи × (цена продажи − средняя).
  При закрытии средняя обнуляется, накопленный реализованный П/У сохраняется.
  Стоимость = количество × последняя цена каталога; нереализованный П/У =
  количество × (последняя цена − средняя). При отсутствии цены или изменении
  валюты полной оценки нет; недостающая цена не считается нулевой.
  Ручной портфель моделирует позиции без денежного счёта/проверки капитала.
- `/history/<id>/`: сохранённые наблюдения, границы дат включительно в UTC,
  таблица, адаптивный график высотой 440 px. Изменение — последняя цена минус
  первая внутри периода; процент относительно первой. Одна точка даёт 0;
  при нулевой первой цене процент не определён. При разных валютах изменение
  не считается, график разделён по валютам. Пустой период объясняется текстом.
  Старые цены каталога не преобразуются в исторические записи: накопление
  начинается с новых обновлений после миграции. Ручной HTML/API ввод цены не
  является рыночным наблюдением. Источник и валюта фиксируются в каждой записи.
- `/strategies/`: стратегия на одну акцию, собственный управляемый портфель,
  начальный капитал в валюте акции, пороги покупки/продажи, количество покупки,
  включение/выключение. Порог продажи строго выше покупки. Покупается заданное
  количество только при пустой позиции и достаточных деньгах; продаётся вся
  позиция. Пирамидинга, коротких продаж и частичного исполнения нет. Правила и
  название можно менять, первоначальный капитал/акция/количество после создания
  неизменяемы. Ручные операции в портфеле стратегии запрещены.
  Итоговая оценка = деньги + стоимость позиции, результат = оценка − начальный
  капитал, доходность = результат / капитал × 100%. Журнал сохраняет также
  отсутствие сигналов и недостаток денег.

Исполнение стратегии — по **цене новой сохранённой котировки** без комиссий,
спреда, проскальзывания, ликвидности, налогов, дивидендов и процентов на деньги.
Это событийная демонстрация, не биржевой эмулятор и не исторический бэктест:
котировки до создания стратегии не торгуются. Пропущенные после создания точки
обрабатываются последовательно по времени; текущие правила применяются к ещё
необработанным точкам. Выключенная стратегия отмечает новые точки обработанными;
при включении они не переигрываются. Для чистой границы изменения правил сначала
выполните `process_investing`, затем изменяйте правила в браузере.

Все денежные вычисления используют Decimal с контекстом 60 цифр. Ввод —
положительное конечное число < 10^18, до 9 дробных знаков. Рыночная цена допускает
ноль (стратегия по нулю не исполняется), < 10^15. Средняя, реализованный результат
и движение денег стратегии округляются до 12 дробных знаков (`ROUND_HALF_EVEN`);
денежный счёт хранится с той же точностью. Предел величин операции/позиции —
10^26. SQLite хранит десятичные строки, PostgreSQL — NUMERIC(38,12).

`dashboard/services/investing.py` — единая бизнес-логика для форм, Celery и команд.
Обновление текущей цены и запись `PriceObservation` атомарны; уникальны
`(share, timestamp)`, принимаются только более новые времена. Исправление той же
временной отметки не заменяет историю. Ручная правка текущей цены не разрешает
повторную запись старых наблюдений. Обработка уведомления/стратегии атомарна с
блокировкой её строки и сохранением последней обработанной котировки. Уникальные
ограничения для уведомлений, журнала и сделок дополнительно защищают повторы.
Покупка/продажа блокирует портфель и выполняется в транзакции; ошибка откатывает
позицию и сделку. Удаление акции, используемой в истории/персональных данных,
возвращает понятную ошибку HTML/API и сохраняет учётные записи.

Все новые персональные списки и прямые URL фильтруются по владельцу; чужой ID
возвращает 404. Нового персонального API нет, общий Share API сохранён. Новые
персональные модели не открыты через admin. Для небольшого локального SQLite
запуска используйте один worker; параллельные процессы могут получать database
locked. Конкурентную эксплуатацию следует проверять на PostgreSQL.

`update_last_price` после обновлений вызывает Celery-задачу `process_investing`
синхронно внутри worker. Beat уже запускает обновление через заданный интервал.
Сбой обработки оставляет котировку в БД, а watermark откатывается: следующая
обработка повторит незавершённую работу. Без Redis доступны те же функции:

```sh
python manage.py update_prices
python manage.py process_investing
python manage.py demo_price DEMO1 100
```

`demo_price` разрешена только для DEMO-инструментов в режиме demo, записывает
котировку и сразу обрабатывает уведомления/стратегии. Можно указать
`--at 2026-11-01T12:00:00Z` для проверки повтора; более старое или равное время
пропускается. Для обычного сценария время не указывайте: используется текущее UTC.
Статический DemoProvider сам не генерирует изменяющиеся цены: `update_prices`
повторную фиксированную цену пропустит. Для изменения demo используйте `demo_price`.

## Полный воспроизводимый ручной сценарий №4

Ниже используется **новый** файл `homework4-manual.sqlite3`, чтобы старые сделки,
история и стратегии не влияли на расчёты. Если такой файл уже есть, выберите другое
новое имя. Существующую БД удалять не нужно. `.env` и `.venv` должны быть созданы
по инструкции первого запуска. Все команды из корня репозитория.

В терминале A:

```sh
source .venv/bin/activate
export MARKET_DATA_SOURCE=demo
export DB_ENGINE=sqlite
export SQLITE_PATH="$PWD/homework4-manual.sqlite3"
python manage.py migrate
python manage.py add_shares
# Начальные цены явно заданы ДО создания стратегии:
python manage.py demo_price DEMO1 100
python manage.py demo_price DEMO2 200
python manage.py demo_price DEMO3 300
python manage.py runserver 127.0.0.1:8765 --noreload
```

В терминале B задайте **тот же путь**:

```sh
source .venv/bin/activate
export MARKET_DATA_SOURCE=demo
export DB_ENGINE=sqlite
export SQLITE_PATH="$PWD/homework4-manual.sqlite3"
```

1. Откройте `http://127.0.0.1:8765/`. Проверьте метку Demo, три цены 100/200/300,
   карточку DEMO1 и читаемые оси свечного графика. Сузьте окно: график должен
   оставаться в ширине карточки. По ссылке «Накопленная история в БД» видна одна
   сохранённая точка DEMO1=100, а не 180 свечей провайдера.
2. Зарегистрируйтесь на `/user/registration/` со своим локальным тестовым email и
   надёжным паролем. В «Наблюдение» добавьте DEMO1, `Цена ≤`, цель **95**.
   Уведомлений пока нет. Повторное добавление той же акции меняет правило.
3. В «Портфели» создайте **Учебный**, валюта **rub**. На его странице последовательно
   купите DEMO1: **2 по 100**, затем **3 по 120**, продайте **2 по 130**.
   Ожидается количество **3**, средняя **112**, реализованный П/У **36**.
   При текущей цене 100 стоимость **300**, нереализованный П/У **−36**.
   Продажа 4, количество 0, отрицательная цена дают ошибки и не добавляют сделок.
4. В «Стратегии» создайте **Пороговая**, DEMO1, купить ≤ **100**, продать ≥ **120**,
   количество **2**, капитал **1000**, включена. Начальная цена 100 была записана
   до создания: сделок пока нет, деньги **1000**, результат **0**.
5. В терминале B выполните:

   ```sh
   python manage.py demo_price DEMO1 90
   python manage.py process_investing
   python manage.py process_investing
   ```

   Обновите страницы. Уведомление одно (90 ≤ 95). У стратегии одна покупка
   **2 × 90**, деньги **820**, позиция 2, средняя 90, стоимость 180, оценка 1000.
   У ручного портфеля стоимость **270**, нереализованный П/У **−66**.
   Повторные `process_investing` не меняют число сделок и уведомлений.
6. В терминале B:

   ```sh
   python manage.py demo_price DEMO1 125
   python manage.py process_investing
   ```
